# 첫 실행 온보딩 설계

## 원칙

첫 실행은 제품 설명보다 행동을 우선한다. 사용자는 설치 후 바로 워크스페이스를 열고 현재 상태를 볼 수 있어야 한다.

온보딩은 다음을 지킨다.

- 필수 질문만 먼저 묻는다.
- 선택 기능은 나중에 설정할 수 있게 둔다.
- 권한, 파일 접근, 네트워크, CLI 실행은 필요한 순간에 설명한다.
- 사용자가 선택을 미뤄도 가능한 작업은 계속 진행한다.

## 화면 1: 시작

주요 버튼:

- 기존 워크스페이스 열기
- Git에서 워크스페이스 가져오기
- 새 워크스페이스 만들기
- 데모로 둘러보기

보조 버튼:

- 개발자 설정
- 최근 워크스페이스

화면 문구는 길게 설명하지 않는다. 워크스페이스를 열면 무엇을 볼 수 있는지만 짧게 말한다.

## 화면 2: 워크스페이스 범위 확인

사용자가 선택한 폴더를 보여주고 다음을 명확히 한다.

- 읽을 문서와 설정 파일
- 생성할 스냅샷과 인덱스
- 실행 가능한 명령 범위
- secret과 token은 자동 수집하지 않는다는 점

## 화면 3: 보기 모드

기본 선택은 `user`다.

옵션:

- `user`: 작업과 히스토리 중심
- `developer`: 설정, 검증, 스펙까지 확인
- `superadmin_developer`: 전체 플랫폼 운영/개발 관점

설명은 짧게 두고, 언제든 설정에서 바꿀 수 있게 한다.

## 화면 4: 준비 상태 검사

필수 검사:

- 워크스페이스 읽기 가능
- 핵심 폴더와 설정 존재
- 스냅샷 생성 가능

선택 검사:

- Git
- Python agent layer
- Node/Next monitor
- Guest CLI adapters on top of the platform
- Slack/Discord/Teams notifications
- Browser automation

선택 검사가 실패해도 대시보드로 갈 수 있어야 한다.

## 화면 5: 대시보드

첫 대시보드는 다음을 보여준다.

- 진행 중인 작업
- 막힌 질문
- 최근 산출물
- 프로젝트 목록
- 새 작업 시작
- 히스토리 보기

사용자가 플랫폼 내부 구조를 이해하지 않아도 작업을 시작할 수 있어야 한다.

## 하지 말아야 할 것

- 첫 실행에서 모든 통합 설정을 강제하지 않는다.
- 사용자가 모르는 용어를 큰 설명 카드로 늘어놓지 않는다.
- 선택 CLI가 없다는 이유로 앱 전체를 막지 않는다.
- 개발자용 raw config를 사용자 모드 첫 화면에 노출하지 않는다.
- 실제 token, webhook URL, browser cookie를 installer에 넣지 않는다.
