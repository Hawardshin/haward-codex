# 구현 계획

## 작업 모드

- 선택: `standard`
- 이유: 데스크톱 UI의 의미 있는 사용성 변경이며 테스트, 빌드, 패키징, 기록, 누락 점검이 필요하다.
- 리소스 위험: CLI/터미널/프로세스 설정 표면을 변경하므로 리소스 점검 기록을 남긴다. 실제 새 프로세스 실행 엔진은 변경하지 않는다.

## 단계

1. 요구사항과 스펙 기록을 남긴다.
2. CLI 어댑터 가이드 모델을 확장한다.
3. 설정 모달의 CLI 어댑터 섹션을 단계형 안내로 바꾼다.
4. Agent CLI Cockpit 카드에 설정 ladder와 명령 복사 행을 추가한다.
5. CSS와 정적 테스트를 추가한다.
6. collect, check, test, build, package를 실행한다.
7. 평가/누락/리소스/요약 기록을 남기고 커밋/푸시한다.

## 옵션 비교

- 옵션 A: README 문서만 보강한다.
  - 장점: 빠르다.
  - 단점: 사용자가 앱 안에서 막히는 문제를 해결하지 못한다.
- 옵션 B: 설정과 Cockpit 안에 단계형 안내를 넣는다.
  - 장점: 사용자가 필요한 순간에 바로 따라갈 수 있다.
  - 단점: UI와 테스트 수정이 필요하다.
- 선택: 옵션 B.

## 언어/런타임 결정

- TypeScript/React: 기존 `workspace-monitor` UI 코드와 테스트 경계에 맞는다.
- Rust/Tauri: 실제 실행 엔진 변경이 아니므로 이번 범위에서는 변경하지 않는다.
