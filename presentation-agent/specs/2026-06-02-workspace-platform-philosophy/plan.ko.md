# Workspace Platform Philosophy 발표 계획

## 선택 모드

- 선택: `standard`
- 이유: 새 플랫폼 정책을 바꾸는 governance 작업은 아니지만, 사용자에게 전달할 의미 있는 발표 산출물과 검증/히스토리 기록이 필요한 작업이다.

## 순서

1. 웹 우선 조사로 외부 보조 근거를 확인한다.
2. 내부 철학, 운영 모델, 기존 발표 팩, 히스토리를 읽고 발표 메시지를 정리한다.
3. 발표 스크립트를 먼저 완성한다.
4. 스크립트를 24장 HTML 덱 구조로 압축한다.
5. `html_deck.py`로 HTML을 생성한다.
6. 단위 테스트, 브라우저 테스트, grounding, omission, evaluator를 실행한다.
7. 히스토리와 작업 요약을 갱신하고 commit/push한다.

## 발표 구조

1. 제목과 한 문장 정의
2. 시작 문제: AI와 일하면 빠르지만 기억과 근거가 사라진다
3. 원인: 대화, 출처, 스펙, 결과, 프로젝트 경계가 흩어진다
4. 철학: 추정은 출발점이고 검색은 인사이트의 원료다
5. 설계: 기록은 다음 에이전트를 위한 인터페이스다
6. 실행 루프: 의도에서 근거, 실행, 평가, 히스토리까지
7. 프로젝트 경계와 도구 독립성
8. 능력 승격과 반복 작업 감소
9. 평가/재작업/가드레일
10. 앞으로의 방향과 결론

## 위험과 대응

- 위험: 내부 히스토리를 너무 많이 넣어 발표가 산만해질 수 있다.
  - 대응: 슬라이드는 핵심 문장 중심, 상세 내용은 speaker notes와 스크립트에 둔다.
- 위험: 외부 출처가 발표 주제를 압도할 수 있다.
  - 대응: 외부 출처는 보조 근거로만 쓰고 내부 문서를 중심으로 둔다.
- 위험: 30분 분량이 부족하거나 과할 수 있다.
  - 대응: 24장, 장당 60-90초를 기준으로 조정 가능한 스크립트로 구성한다.
