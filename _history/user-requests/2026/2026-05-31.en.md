## Accumulated Operating Principles

- User requests should live in repository documents, not only chat memory.
- Prefer summaries of meaning, durability, and implementation location over full original text.
- Request summaries should connect to outcomes, artifacts, evaluations, and commits through request-to-outcome traces.
- User requests may become requirement candidates and should be turned into baselines, changes, and reviews before implementation when they affect expected behavior.
- Meaningful implementation work should turn requirements into spec-driven artifacts before coding.
- Skill creation and updates should close with source, trigger examples, validation, forward tests, and improvement ideas.
- Source-code work must check architecture references and record at least two structure options plus the decision rationale.
- Large-company engineering, official research lab, architecture center, and high-signal independent sources should be managed in a separate registry and source list.
- Material values, review signals, claims, config values, assumptions, and planning constraints must be traced to sources and access dates; plan steps must connect to evidence.
- Global, Korean, India, paper, and Korean local review search origins are managed in `source-discovery-registry.json`; Korean-user review judgment is scored with `_tools/korean-local-review/`.
- Durable instructions must be reflected in `AGENTS.md`, `README.md`, `_docs/persistent-instructions.*`, and relevant operating docs.
- Future work closes with web search, memory bootstrap, request summary updates, requirements check/update, spec check/update, source discovery or enterprise source registry review when useful, architecture option comparison for code work, Korean local review scoring when useful, skill validation/improvement when needed, implementation, verification, request-to-outcome trace, evaluation, commit, and push.
