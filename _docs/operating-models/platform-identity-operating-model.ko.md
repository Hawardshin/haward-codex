# 플랫폼 아이덴티티 운영 모델

## 한 문장

이 플랫폼은 사용자의 의도를 근거 있는 계획과 검증 가능한 결과로 바꾸고, 인간이 반복하는 작업 프로세스를 모델링해 더 효율적인 방법과 자동화 자산으로 축적하는 개인 AI 에이전트 작업 운영체계다.

## 왜 존재하는가

AI와 함께 일하면 빠르게 만들 수 있지만, 빠르게 잊기도 쉽다. 대화 속에서 나온 판단은 시간이 지나면 사라지고, 어떤 출처를 믿었는지 흐려지고, 스펙과 소스와 실제 결과가 어긋나도 바로 보이지 않는다. 프로젝트가 늘어날수록 이 문제는 더 커진다.

이 저장소는 그 흐름을 반대로 만들기 위해 존재한다. 사용자의 지시는 요구사항으로 남고, 요구사항은 스펙과 계획으로 좁혀지며, 구현은 검증과 평가를 통과하고, 결과는 히스토리와 커밋으로 이어진다. 한 번의 좋은 답변이 아니라, 사람이 같은 일을 반복하는 시간을 줄이고 시간이 지날수록 더 똑똑해지는 작업 환경이 목표다.

## 핵심 정체성

이 플랫폼은 여러 성격을 동시에 가진다.

### 1. 에이전트 구축 플랫폼

`agent-platform/`은 조사, 계획, 평가, grounding, 메모리 부트스트랩, 설정 검증, 알림, 오픈소스 검토 같은 공통 능력을 제공한다. 새 에이전트는 이 공통 능력을 재사용해 더 빨리 만들어지고, 더 일관된 기준으로 평가된다.

### 2. 프로젝트 운영 monorepo

발표 에이전트, 모니터링 사이트, 조사 도구, 로컬 리뷰 도구처럼 관심사가 다른 작업은 독립된 루트 프로젝트로 관리한다. 프로젝트마다 README, docs, specs, src, tests, artifacts를 갖고, 공통 자산만 `_docs`, `_ops`, `_tools`, `_skills`, `_research`, `_history`로 승격한다.

### 3. 장기 기억과 증거 시스템

웹 검색 기록, 출처 목록, 요구사항, 스펙, 계획, 작업 요약, 평가, 설치 감사, 커밋 해시는 모두 다음 작업의 기억이다. 이 기억은 무조건 믿는 지식 베이스가 아니라, 다시 검증할 수 있는 증거 핸들이다.

### 4. 반복 작업 감소 엔진

플랫폼은 사람이 실제로 하는 프로세스를 흉내 내는 데서 멈추지 않는다. 조사, 비교, 판단, 실행, 검증에서 반복되는 동작을 찾아 더 효율적인 순서, 더 작은 도구, 더 좋은 프롬프트, 더 명확한 템플릿으로 바꾼다. 목표는 자동화를 늘리는 것이 아니라 사람의 반복 작업과 소요 시간을 줄이는 것이다.

### 5. 비정형 데이터를 정형 자산으로 바꾸는 변환 레이어

AI는 흩어진 대화, 긴 문서, 조사 자료, 리뷰, 로그, 메모 같은 비정형 입력에서 구조를 찾는 데 강하다. 플랫폼은 이 능력을 사용해 사용자의 말과 자료를 요구사항, 스펙, 태스크, evidence item, 표, JSON, 평가 입력으로 바꾼다. 단, 구조화된 출력은 출처와 검증이 붙을 때만 신뢰 가능한 자산으로 다룬다.

### 6. 설치형이지만 CLI에 종속되지 않는 실행 레이어

플랫폼은 사용자가 설치해서 쓰는 제품으로 발전할 수 있지만, 특정 CLI wrapper가 되면 안 된다. 설치형 앱은 작업 공간, 히스토리, 문서, 평가, 설정, UI를 제공하고, Codex CLI, Claude Code, GitHub CLI, package manager, 배포 CLI 같은 외부 명령은 교체 가능한 adapter capability로 붙인다. CLI가 없으면 플랫폼 전체가 멈추는 것이 아니라 해당 capability만 unavailable로 표시하고 대체 경로를 안내한다.

## 작동 원리

```text
의도 수집
  -> 웹 우선 조사
  -> 메모리 부트스트랩
  -> 작업 모드 선택
  -> 요구사항/스펙/계획
  -> 실행
  -> 검증/grounding
  -> 평가/재작업
  -> 히스토리/커밋/push
  -> 반복 능력 승격
```

이 루프의 목적은 문서를 많이 만드는 것이 아니라 판단을 잃지 않는 것이다. 빠른 작업에는 가벼운 모드를 쓰고, 구조와 정책과 외부 근거가 중요한 작업에는 더 엄격한 모드를 쓴다.

루프가 반복되면 반복 자체를 관찰한다. 같은 조사, 같은 파일 탐색, 같은 검증, 같은 보고서 작성이 반복되면 먼저 프로세스를 문서화하고, 그다음 자동화 가능한 최소 단위로 쪼개 도구/스킬/템플릿 후보로 만든다.

## 좋은 산출물의 기준

좋은 산출물은 단순히 동작하거나 보기 좋은 결과가 아니다. 이 플랫폼에서는 다음 조건을 만족해야 한다.

- 왜 만들었는지 요구사항과 연결된다.
- 어떤 근거를 참고했는지 출처가 남아 있다.
- 어떤 선택지를 버렸는지 계획 또는 결정 기록에서 확인할 수 있다.
- 검증 방법과 결과가 남아 있다.
- 평가가 초기 지시와 결과의 차이를 확인한다.
- 나중에 다시 열어도 어디서부터 이어갈지 알 수 있다.

## 플랫폼이 멋있어져야 하는 방향

이 플랫폼의 미학은 화려한 자동화보다 선명한 구조에 있다. 폴더 이름만 봐도 역할을 알 수 있고, 설정 파일만 열어도 왜 존재하는지 이해할 수 있으며, 히스토리만 읽어도 요청과 결과와 커밋이 연결되어야 한다.

장기적으로는 다음 모습에 가까워져야 한다.

- 사용자가 “무엇을 만들고 싶은지” 말하면 에이전트가 먼저 좋은 질문과 조사 계획을 만든다.
- 에이전트는 비정형 지시와 자료를 schema, provenance, validation이 있는 정형 기록으로 바꾼다.
- 조사 에이전트는 공식 문서, 논문, 기술 블로그, 커뮤니티 신호, 한국 로컬 소스까지 넓게 보고 근거를 정리한다.
- 구현 에이전트는 언어, 아키텍처, 폴더 구조, 오픈소스 후보를 비교한 뒤 유지보수 가능한 방향으로 만든다.
- 실행 레이어는 여러 CLI를 활용하되 특정 CLI에 종속되지 않고, adapter contract와 permission boundary로 교체 가능성을 유지한다.
- 평가 에이전트는 초기 의도와 결과를 비교하고, 부족한 부분은 다시 작업으로 돌린다.
- 모니터링 UI는 히스토리, 프로젝트, 스펙, 평가, 진행 중인 작업을 한눈에 보여준다.
- 반복되는 좋은 흐름은 스킬과 도구와 템플릿으로 승격되어 다음 작업을 더 빠르고 정확하게 만든다.
- 반복 작업이 실제로 줄었는지 작업 시간, 병목 기록, evaluator 결과로 확인한다.

## 중요한 경계

이 플랫폼은 에이전트의 자율성을 키우지만, 최종 권한은 사용자에게 있다. 보안, 프라이버시, 공개 배포, 비용, 되돌리기 어려운 변경은 명시적으로 다룬다. 또한 저장된 지식도 틀릴 수 있다고 보고, 중요한 판단에는 항상 최신 출처와 검증을 붙인다.
